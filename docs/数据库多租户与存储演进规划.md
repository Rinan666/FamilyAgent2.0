# 数据库多租户与存储演进规划

**日期**：2026年6月4日  
**适用范围**：FamilyAgent 的题库资源、家族私有知识、日记、长期记忆、镜像 Agent 数据  
**定位**：明确“无数家族的私有数据”如何存储、隔离和扩容。

---

## 一、核心结论

FamilyAgent 后续确实需要区分两类知识库：

1. **题目资源库 / 教育资源库**：服务测试生成、AI家教讲题、多学科题目与资料管理。
2. **家族个性化知识库 / 长期记忆库**：服务日记、对话记忆、学习风格、性格画像、家族经验和镜像 Agent。

但工程上不应该一开始就为每个家族创建一个独立数据库。

推荐路线：

```text
早期：共享 PostgreSQL + family_id / user_id / visibility 隔离
中期：按 family_id 分区或分片
后期：少数高隐私/大体量家族使用独享数据库
```

---

## 二、当前阶段策略

Phase 1 到 Phase 2 初期采用：

```text
一个 PostgreSQL 集群
多个逻辑模块
统一多租户隔离字段
```

所有家族私有数据表都应逐步具备：

| 字段 | 作用 |
|------|------|
| `family_id` | 数据所属家族，作为租户隔离主键 |
| `user_id` / `author_id` | 数据所属用户或创建者 |
| `visibility` | 可见范围，例如 `PUBLIC`、`PRIVATE`、`FAMILY` |
| `permission_scope` | 更细粒度权限，例如可见成员、角色、授权用途 |
| `source` | 数据来源，例如用户输入、AI生成、导入、家族访谈 |
| `metadata` | 未来扩展字段 |

当前已在 schema 中为题库、测试记录、学力档案、会话、日记、家族知识、镜像数据补充这些方向的字段。

---

## 三、数据边界

### 3.1 公共教育资源

公共题库可以 `family_id = NULL` 且 `visibility = PUBLIC`。

典型数据：

- 系统种子题库。
- 通用数学题。
- 后续公开教材资料。
- AI生成但审核后可复用的公共题。

### 3.2 家族私有资源

家族上传或沉淀的数据应带 `family_id`。

典型数据：

- 某个家族上传的私有题目。
- 孩子的测试记录。
- AI家教对话摘要。
- 日记。
- 长辈技能与经验。
- 家族故事、处世心法、人生事件思考。
- Mirror Agent 长期记忆。

### 3.3 用户私有数据

某些数据属于用户本人，但可以选择是否进入家族视角。

典型数据：

- 个人日记。
- 学习风格偏好。
- 性格特征记忆。
- 私密对话摘要。

这类数据应至少带 `user_id` 和 `visibility = PRIVATE`，需要进入家族共享时再赋予 `family_id` 或更新权限。

## 四、扩容路线

### Phase 1：共享库

目标：

- 一个 PostgreSQL。
- 所有私有表预留 `family_id`、`visibility`、`permission_scope`。
- 查询私有数据时必须带 `family_id` 或 `user_id`。

### Phase 2：权限与记忆完善

目标：

- 后端服务层统一做家族成员校验。
- 向量检索必须携带 `family_id` / `user_id` 过滤条件。
- MinIO 文件路径按家族隔离。
- Redis key 带租户前缀。
- 记录审计日志。

### Phase 3：分区

数据量增长后，优先考虑 PostgreSQL 分区。

可选策略：

```text
按 family_id hash 分区
按 created_at 时间分区
按资源类型分区
```

优先适用表：

- `diary_entries`
- `family_knowledge`
- `chat_sessions`
- `test_records`
- 未来的 memory chunks / resource documents

### Phase 4：分片

当单个 PostgreSQL 集群无法承载时，建立租户路由。

路由表：

```text
tenant_storage_routes
```

用于记录：

- `family_id`
- 存储层级 `SHARED` / `SHARDED` / `DEDICATED`
- 数据库别名
- schema 名称
- MinIO bucket 前缀
- 向量命名空间
- 加密密钥引用

应用层通过 `family_id` 找到具体存储位置。

### Phase 5：独享库

少数家族可以迁移到独享数据库。

适用条件：

- 数据量极大。
- 高隐私或合规要求。
- 付费大客户。
- 需要独立备份、删除、加密密钥和审计。

独享库不应成为默认方案，而应是高级租户形态。

## 五、当前代码约束

近期开发需要遵守：

1. 公共题库查询默认只读 `visibility = PUBLIC` 或 `family_id IS NULL` 的题目。
2. 测试记录、学力档案、AI家教会话默认 `visibility = PRIVATE`。
3. 家族知识默认 `visibility = FAMILY`。
4. 未来新增私有表必须带 `family_id`、`user_id` 或明确说明为何不需要。
5. 后续实现向量检索时，不能只按相似度查，必须带租户过滤条件。
6. 用户级接口默认只允许当前登录用户访问自己的数据；未来家长访问孩子档案时，应通过家庭角色授权扩展，而不是直接信任请求里的 `userId`。
7. 新增用户级接口时优先提供 `/me` 形态，由后端登录态决定用户身份；旧的 `/{userId}` 形态只作兼容入口，并必须保留本人校验。
8. 请求中携带 `family_id` 时，后端必须校验当前登录用户属于该家族，不能只校验 `user_id`。

## 六、迁移说明

首次初始化数据库使用：

```text
scripts/init-db.sql
```

已经存在的本地或开发数据库，需要执行：

```text
scripts/migrate-multitenant-storage.sql
```

该迁移脚本使用 `IF NOT EXISTS`，可以重复执行。

## 七、推荐命名

建议在项目中使用以下术语：

| 中文 | 英文 | 说明 |
|------|------|------|
| 教育资源库 | Education Resource Store | 公共或家族私有的题目与资料 |
| 家族记忆库 | Family Memory Store | 家族知识、日记、长期记忆 |
| 多租户共享库 | Multi-Tenant Shared Database | 当前默认数据库形态 |
| 租户路由 | Tenant Storage Routing | 后续分片/独享库入口 |
| 独享租户库 | Dedicated Tenant Database | 少数高价值/高隐私家族使用 |
